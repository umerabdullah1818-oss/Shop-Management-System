# Database Schema — Phase 4

Status: draft for review. Full ERD, PostgreSQL/Prisma schema. Builds on `04-database-erd-plan.md`. The actual schema lives in [`packages/database/prisma/schema.prisma`](../packages/database/prisma/schema.prisma) — this document explains the design decisions behind it. Defining the schema is a Phase 4 deliverable per §55; no application code (services, controllers, business logic) is written yet — that's Phase 8.

## 2. Identifier strategy

Per `OFF-004`/`SYNC-001`/`SYNC-003`: every row that can be created on the Local Shop Server while offline needs a globally unique, collision-proof ID that isn't dependent on a database sequence — because a database sequence is exactly the "won't collide" guarantee we *don't* have across an offline period between shops... except this system has only one shop and one writer (the Local Shop Server itself, per Decision #16/#4), so sequence collision *within* one local Postgres was never actually the risk. The real reason is **cloud upsert idempotency** (`SYNC-003`): the cloud must be able to receive the same event twice (retry) and treat it as a no-op, which requires the ID to be assigned *before* the cloud ever sees it, i.e., client-side (local-server-side) at creation time.

- **Decision**: all financially/operationally significant entities (`Sale`, `SaleItem`, `Purchase`, `InventoryBatch`, `InventoryMovement`, `Payment`, `KhataTransaction`, `Return`, `SupplierPayment`, `OutboxEvent`, etc.) use a **ULID** as their primary key, generated by a shared application-level `IdService` at creation time — not a Postgres `SERIAL`/`uuid()` default. ULIDs are lexicographically sortable by creation time (useful for FIFO-adjacent debugging/ordering) and collision-resistant like a UUID.
- Reference/config data with no offline-sync relevance (`Category`, `Settings`, `Device`) can use Prisma's `cuid()` default — simpler, and it doesn't matter here since these aren't part of the sync-critical financial path.
- **Human-readable invoice numbers** (`Sale.invoiceNumber`) are a *separate* field from the primary key, generated per the `SHOP-C{counter}-{year}-{sequence}` scheme (Decision #5) — the sequence portion is a local-server-side counter scoped per `Counter`, safe because the Local Shop Server is the sole writer.

## 3. FIFO & historical immutability — the design that makes §14/§15/§16 actually hold

- `InventoryBatch.unitCost` and `InventoryBatch.createdAt` are **write-once**: no service method will ever expose an update path for them. FIFO order is always `ORDER BY createdAt ASC` (or `originalSequence` — see index note below) among batches with `remainingQty > 0` for a given product.
- `SaleItemBatchAllocation` is the linchpin table: one row per (sale item, batch) pair actually consumed, storing `quantity` and `unitCostAtSale` **copied at the moment of sale** — so even if `InventoryBatch.unitCost` were somehow queried later, the historical COGS calculation never depends on it still matching; it depends only on this allocation snapshot. This is what makes `AC-011` (multi-batch COGS correctness) and `BR-015` (historical prices never change) both provable rather than "hopefully true."
- `SaleItem.unitPrice` (actual selling price charged) and `SaleItem.officialPriceAtSale` (snapshot of the product's official price at that moment) are both stored on the row — so a later change to `Product.officialPrice` never touches historical invoices (`BR-015`), and reports can still show "sold below/above official price" without re-deriving anything.
- Returns restock the **original batch** (Decision #3 / `BR-017`): `ReturnItemBatchRestock` mirrors `SaleItemBatchAllocation` — a return of quantity *N* from a sale item that was originally split across two batches produces up to two restock rows, proportional to the original split, incrementing each original batch's `remainingQty` back up. This is only possible *because* `SaleItemBatchAllocation` recorded exactly which batches were touched.

## 4. Audit & Sync structure

- `AuditLog` is **append-only by database grant**, not just by convention: the application's Postgres role gets `GRANT INSERT` only on this table, no `UPDATE`/`DELETE` (`SEC-006`). It references its subject polymorphically (`entityType` + `entityId` as plain strings, no FK) because it must be able to point at *any* table, including ones that get soft-deleted/disabled later — an FK would either block that or require `ON DELETE SET NULL`, which would corrupt the audit trail's meaning.
- `OutboxEvent` (the sync queue) is written inside the **same transaction** as the business row it describes (transactional outbox — `SYNC-001`). It's also polymorphic (`entityType`/`entityId`) for the same reason, plus it carries a full JSON `payload` snapshot so the sync worker never has to re-query "what did this look like at the time" from a row that may have since changed (e.g., a batch's `remainingQty` continuing to drop after the event was queued).
- `OutboxEvent.state` enum matches `SYNC-004` exactly: `LOCAL_ONLY, PENDING_SYNC, SYNCING, SYNCED, SYNC_FAILED, CONFLICT`.
- `SyncConflict` references `OutboxEvent` by FK (conflicts are always about a specific queued event) and is expected to be rare-to-empty under the confirmed single-writer architecture — it exists as the safety net `SYNC-004` requires, not as a heavily-used table.

## 5. Constraints worth calling out explicitly

- **Unique**: `Product.sku`, `Product.barcode` (nullable-unique — Postgres allows multiple `NULL`s under a unique index, so "no barcode" doesn't collide with another "no barcode"), `User.username`, `Sale.invoiceNumber`, `KhataAccount.customerId` (1:1), `PurchaseItem.id` ↔ `InventoryBatch.purchaseItemId` (1:1).
- **One open shift per counter** (`BR-021`): this can't be expressed as a plain Prisma `@@unique` because it's conditional on `status = OPEN`. It's implemented as a **Postgres partial unique index**, added via a manual migration:
  ```sql
  CREATE UNIQUE INDEX one_open_shift_per_counter
    ON "Shift" ("counterId")
    WHERE status = 'OPEN';
  ```
- **Foreign keys default to `RESTRICT`** (not `CASCADE`) on delete everywhere financial history is involved — e.g., you cannot delete a `Product` that has any `InventoryBatch`, `PurchaseItem`, or `SaleItem` referencing it. Combined with `BR-001` (soft-delete only via `status`), hard deletion of anything historically referenced is blocked at both the application layer and the database layer.
- **Indexes** added beyond the automatic ones on FK columns: `InventoryBatch(productId, remainingQty)` for fast "find next FIFO batch" queries; `Sale(occurredAt)` and `Sale(customerId, status)` for reporting/Khata queries; `AuditLog(entityType, entityId)` and `AuditLog(createdAt)`; `OutboxEvent(state)` and `OutboxEvent(createdAt)` for the sync worker's polling query and health check (`SYNC-006`).

## 6. Money & enums

- All monetary columns are `Decimal @db.Decimal(12, 2)` in Prisma (maps to Postgres `NUMERIC(12,2)`) — never `Float`/`Int` cents-as-float, per `NFR-012`.
- Enums used: `UserRole`, `EntityStatus`, `PurchasePaymentStatus`, `BatchStatus`, `MovementType`, `PaymentMethod`, `SaleStatus`, `ShiftStatus`, `KhataTransactionType`, `SyncState`, `ExpenseCategory`, `DeviceType`, `ReturnStatus` — all defined in the schema so invalid string values are rejected at the database level, not just in application validation.

## 7. Amendments made during implementation

- **`KhataPayment.shiftId`, `Return.shiftId`, `Expense.shiftId`** (all nullable): discovered missing while implementing shift cash reconciliation (`FR-092`). The expected-cash formula needs "cash Khata collections," "cash refunds," and "cash expenses" scoped to *this specific shift*, which isn't derivable from a time-window guess once more than one counter can be open at once. Nullable because Admin can record any of these outside an active shift (e.g. a back-office Khata collection).
- **`Expense.paymentMethod`** (required, no default): the original spec's expense field list (§29) doesn't include a payment method, but `FR-092`'s formula can't subtract "cash expenses" without knowing which expenses were paid in cash. Deliberately made required rather than defaulted to `CASH`, so shift math is never silently wrong because of an assumption — whoever records the expense states how it was paid.
- **Outbox processing order uses `id` (ULID), not `createdAt`**: discovered while implementing the sync worker. Postgres's `now()` is stable for an entire transaction, so several `OutboxEvent` rows written within one sale/return/purchase transaction all get the *same* `createdAt` — `ORDER BY createdAt` can't reliably preserve the order dependent rows need (e.g. a `SaleItem` must reach the cloud after its `Sale`). The ULID `id` is generated in application code at each individual call, so it's the value that actually reflects true creation order; the worker orders by it instead (`apps/local-server/src/sync/sync-worker.service.ts`).
- **Cross-app `DATABASE_URL` collision (found via a real runtime smoke test, not just type-checking)**: `local-server` and `cloud-api` both import the same generated Prisma client from `@shop/database`. That generated client auto-loads `packages/database/.env` (since that's where `schema.prisma` lives) the moment it's first imported — before either app's own `ConfigModule` gets a chance to run, and since `dotenv` never overrides an already-set variable, each app's own `DATABASE_URL` was silently ignored in favor of `packages/database/.env`'s. `local-server` appeared to work purely by coincidence (its intended value happened to match). `cloud-api` did not: every "successful" sync was silently writing into the *local* database instead of the cloud one, while `/health` and the API response both reported success — the kind of bug that's invisible without actually querying the target database directly. Fixed two ways together: (1) each app's `PrismaService` now passes `datasources.db.url` explicitly rather than trusting Prisma's own resolution, and (2) each app's `dev`/`start` scripts use `dotenv-cli` (`dotenv -e .env -o -- ...`) to load that app's own `.env` into the real OS process environment *before* Node starts, so the pollution never gets a foothold. Worth remembering for any future app added to this monorepo that touches `@shop/database`.
- **`Counter` needed a deterministic id and real sync support.** Originally treated as "fixed physical setup" not worth syncing (§2's ULID-vs-`cuid()` split). Wrong: `Shift` and `Sale` both hold a hard FK to `counterId`, so a counter that only exists on one side breaks sync for everything that references it — caught by the runtime smoke test's FK safety net (`Shift_counterId_fkey` violation on the cloud side), not by type-checking. Fixed by giving the seed's bootstrap counter a deterministic id (`SEED-counter-c1`, matching across environments the same way the seed admin/walk-in-customer already did) and adding a real `POST /counters` endpoint with outbox recording for any counter created after that.
- **`User` rows are deliberately never synced.** Each environment (local, cloud) provisions its own Users independently via the seed script rather than through the outbox — there's no `POST /users` endpoint yet (Phase 8's Users CRUD module), and syncing user/credential data outward has its own security questions (should a cashier's PIN hash leave the shop's local server at all?) worth resolving deliberately rather than by default. Practical consequence: any row with a FK to `User` (`Sale.cashierId`, `Purchase.createdById`, `AuditLog.userId`, ...) will fail to sync with a foreign-key error until the referenced user exists on the cloud side too — by design, surfaced clearly as a sync failure rather than silently dropped or nulled out. Revisit if/when remote user management becomes a real requirement.
- **Partial-return batch order** (implemented in `ReturnsService`): Decision #3 settled *that* returns restock the original batch(es), but not the order when a partial return doesn't need all of them. Implemented rule: restock the *most recently consumed* batch first (i.e. undo the original FIFO consumption in reverse) — simple, deterministic, and avoids fractional/proportional splitting across batches.
